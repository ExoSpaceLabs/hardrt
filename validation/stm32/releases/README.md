# Release qualification packages

`validation/stm32/releases/` is the gitignored local retention area for the **required selected physical qualification package** of each release (0.6.0 and later), for example:

```text
validation/stm32/releases/0.5.0/
validation/stm32/releases/0.6.0/
```

The local directory mirrors the Git release-tag convention; the corresponding repository tags are `0.5.0`, `0.6.0`, and so on.

These directories are gitignored. Do **not** commit generated hardware evidence after qualification, because doing so would change the source SHA that was physically tested.

For a release:

1. qualify the final candidate source on NUCLEO-H755ZI-Q, preserving the full
   unfiltered report and raw GDB/OpenOCD logs locally;
2. update root `VERSION` and matching release notes, then promote to `main`;
3. **GitHub Actions automatically** waits for all three green current-main CI
   workflows, creates the immutable VERSION tag, builds packages and **publishes**
   the GitHub Release, recovering any existing draft without manual intervention.

The optional local evidence package can be built with:

```bash
./scripts/package_stm32_qualification.sh X.Y.Z validation/stm32/<UTC>_<short-sha>
```

For extra local verification use
`./scripts/finalize_release.sh X.Y.Z validation/stm32/<UTC>_<short-sha>`.
These archival helpers do **not** gate software release publication, upload
physical files, change branches, or fabricate hardware results. Hardware logs
retained only on the operator's computer are not accessible to GitHub CI.

The package helper creates only:

```text
hardrt-stm32-qualification-X.Y.Z.tar.xz
hardrt-stm32-qualification-X.Y.Z.tar.xz.sha256
```

The `.tar.xz` contains the report and all raw logs, but neither the archive nor the unpacked logs are tracked by Git. The GitHub Release is automatically published with validated software assets. Optional physical evidence files remain in local retention unless explicitly provided to a remotely accessible artifact store.

Do not qualify a temporary feature/release branch. Do not retain ad-hoc failed or partial runs as release packages. Development evidence belongs under the timestamped `validation/stm32/<UTC>_<short-sha>/` locations generated by the runner.

See [`docs/RELEASE_PROCESS.md`](../../../docs/RELEASE_PROCESS.md) for the complete end-to-end release procedure.
