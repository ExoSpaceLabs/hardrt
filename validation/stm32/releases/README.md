# Release qualification packages

`validation/stm32/releases/` is the optional local retention area for one selected physical qualification package per release, for example:

```text
validation/stm32/releases/0.5.0/
validation/stm32/releases/0.6.0/
```

The local directory mirrors the Git release-tag convention; the corresponding repository tags are `0.5.0`, `0.6.0`, and so on.

These directories are gitignored. Do **not** commit generated hardware evidence after qualification, because doing so would change the source SHA that was physically tested.

For a release:

1. merge all target/build-affecting changes into `develop` and freeze one release-candidate SHA there;
2. run `scripts/stm32_manual_test_full.sh` unfiltered on that exact SHA;
3. inspect the complete passing report and raw logs;
4. package the selected run with:

   ```bash
   ./scripts/package_stm32_qualification.sh X.Y.Z validation/stm32/<UTC>_<short-sha>
   ```

5. promote/tag the release according to [`docs/QUALIFICATION.md`](../../../docs/QUALIFICATION.md);
6. let `.github/workflows/release.yml` create the draft GitHub Release and software packages;
7. publish the physical evidence and finish branch cleanup with:

   ```bash
   ./scripts/finalize_release.sh \
     X.Y.Z \
     validation/stm32/<UTC>_<short-sha> \
     --cleanup-branches
   ```

The package helper creates only:

```text
hardrt-stm32-qualification-X.Y.Z.tar.xz
hardrt-stm32-qualification-X.Y.Z.tar.xz.sha256
```

The `.tar.xz` contains the report and all raw logs, but neither the archive nor the unpacked logs are tracked by Git. The GitHub Release is the publication boundary for physical evidence.

Do not qualify a temporary feature/release branch. Do not retain ad-hoc failed or partial runs as release packages. Development evidence belongs under the timestamped `validation/stm32/<UTC>_<short-sha>/` locations generated by the runner.

See [`docs/RELEASE_PROCESS.md`](../../../docs/RELEASE_PROCESS.md) for the complete end-to-end release procedure.
